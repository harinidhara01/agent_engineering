**1. (Terminology)** What is the difference between a metric and a release gate (§10.3–10.4)?
- A) They're interchangeable terms for the same thing
- **✓** B) A metric measures something about system behavior; a gate applies thresholds to metrics to produce a ship/don't-ship decision
- C) A metric only applies to model quality, never to code quality
- D) A gate is computed by a human; a metric is always automated

**2. (Terminology)** Why does a golden dataset need to be version-controlled, not regenerated fresh each run?
- **✓** A) A gate result is only meaningful if you can compare it against the same fixed set of cases over time — a dataset that changes silently makes "passed" mean something different each run
- B) Version control is required by ADK for any dataset used in testing
- C) It doesn't need to be — regenerating it each run is actually preferred
- D) Golden datasets are always generated by the model itself, never hand-authored

**3. (Architecture)** Why does `GOLDEN_DATASET` deliberately include an injection-attempt case and a conflicting-evidence case, not just qualified/disqualified pairs?
- **✓** A) Because those are exactly the failure modes this course has already shown can break the system — a golden dataset that skips them isn't testing anything hard
- B) Because ADK requires at least ten categories in any golden dataset
- C) Injection-attempt cases are only relevant for security audits, not release gates
- D) Conflicting-evidence cases are included purely for documentation, not actually run

**4. (Architecture)** Why does `check_release_gate()` collect and report every failing reason instead of stopping at the first one?
- **✓** A) So a single run gives the complete picture — fixing one issue and re-running to discover a second one wastes a cycle a full report would have prevented
- B) Because Python's exception handling requires collecting all errors before raising
- C) It doesn't — stopping at the first failure is the correct, recommended behavior
- D) Only for performance reasons; there's no correctness benefit

**5. (Failure analysis)** A release gate passes, but a real account later breaks the system in a way the golden dataset never covered. Is the gate wrong?
- **✓** A) Not necessarily — the gate can only prove the system meets its own known bar; a coverage gap in the dataset is a separate problem from an incorrect gate, and the fix is usually adding a new golden-dataset case
- B) Yes, always — any real failure means the gate's logic was broken
- C) No — release gates are only ever approximate and can't be improved
- D) The gate should be deleted since it clearly can't be trusted

**6. (Security/governance)** What does "fails loudly" mean for a release gate, concretely?
- **✓** A) A failure produces a clear, specific, named reason a person can act on — never a silent pass, and never a vague "something's wrong"
- B) The gate prints a warning to stderr but otherwise still allows deployment
- C) It means the gate should page an on-call engineer immediately for every failure
- D) It's a synonym for "fails accurately," with no distinct meaning of its own

**7. (WidgetWare scenario)** `approval_compliance_rate()` only recognizes four workflow states at this checkpoint. What happens once Class 10 adds two more?
- **✓** A) The metric will need to be updated to account for the new states, or it will silently miscount runs that land in states it doesn't recognize — a documented, known gap at this checkpoint
- B) Nothing — the metric automatically adapts to any new state added later
- C) The release gate will crash the moment a new state is introduced
- D) The two new states replace the four existing ones entirely

**8. (Connecting back)** How does the release gate's category-by-category structure reuse the idea behind Class 5's business invariants?
- **✓** A) Both replace one large, hard-to-verify "trust it" judgment with several small, individually checkable conditions
- B) They're unrelated — invariants apply to single results, gates apply to entire deployments, with no shared design principle
- C) The release gate replaces the need for business invariants entirely
- D) Business invariants only matter once a release gate already exists
